# ADR-002: サーバー権威境界とEdge Function実行方式

- 状態: 承認済み
- 関連Issue: #502・#511

## 文脈

現在、XP・レベル・装備・宝箱などの価値はすべてクライアント（Zustandストア）で計算・確定している。クラウド化にあたり、クライアント入力を信用しない構造が必要になる。一方でゲームルール（XPテーブル・ガチャ抽選・売却額・繰り返し生成規則）は `@life-quest/core`（純TS、React/Zustand/DOM非依存）に共有実装として集約済みであり、これをSQL（plpgsql）へ再実装すると二重実装になり数値が乖離するリスクがある。

## 決定

1. **価値を増減させる操作（XP・報酬・インベントリ・宝箱・バトル報酬・実績）はすべてサーバーで検証・確定する。** クライアントはIDと冪等キーのみを送る。
2. **ゲームルールの数値計算はコード上ただ1箇所（`@life-quest/core`）に保つ。** 報酬・進行を扱うサーバー処理はSupabase Edge Functions（Deno）として実装し、coreを直接importして実行する。PostgreSQL関数はトランザクション・制約・冪等性管理・所有者検証のみを担当し、ルール計算をしない。
3. Edge Function中心の構成（案B）が技術的に成立するか（Denoからのnpmワークスペースcore解決・単一トランザクション・同時冪等・ロールバック無残留）は**#511のスパイクで実証してから確定する**。不成立の場合は本ADRへ差し戻して再決定する。

## 却下した代替案

- **plpgsqlへのルール再実装（案A）**: coreとの二重実装によるドリフトリスクが是正不能のため原則不採用。
- **クライアント計算値をそのまま信頼して保存**: 改ざん・二重報酬を防げない。

## 帰結

- Edge Functionsのコールドスタート（数百ms）を許容する
- coreのESM/Deno互換性を#511で検証する必要がある
- core-vs-Edge Functionパリティテスト（同一入力で同一出力）を継続的に実行する（#507）
