# ADR-005: 同期バージョニングとカーソルの取りこぼし特性

- 状態: 承認済み
- 関連Issue: #501・#504・#511

## 文脈

クライアントがサーバーの変更を差分取得するためのカーソル機構が必要。設計過程で2つの誤った案を却下した経緯ごと記録する。

### 却下1: `updated_at`（壁時計）カーソル

同一トランザクション内の複数行が同じ時刻を持つ境界問題に加え、同時実行トランザクションのコミット順と時刻代入順が一致しないため取りこぼす。

### 却下2: グローバルシーケンス `nextval()`

シーケンスの採番順とコミット順は一致しない。採番が早くてもコミットが遅い「取り残されたトランザクション」が発生し、クライアントが先へ進めたカーソルより手前に未観測の行が出現する。

### 重要な特性の訂正（設計レビューで確定）

一度カーソルが高いversionまで前進した後に、それより低いversionを持つ行が遅れてコミットされて現れた場合、**その行は `version > cursor` の条件に二度と合致せず、恒久的に回収不能になる。**「カーソルは実際に返った行の最大versionにのみ前進させれば後から拾える」という初期案の想定は誤りである。したがって「低いversionが後から現れる」状況を**発生させないこと**が唯一の防波堤であり、カーソル前進ポリシーは救済策にならない。

## 決定

- **ユーザー単位のバージョン行**（`sync_versions.current_version`）を、`next_sync_version(user_id)` 関数内で行ロック（UPDATE）によりインクリメントする。ロックは呼び出し元トランザクションのコミット/ロールバックまで保持されるため、**同一ユーザーの書き込みトランザクションは採番順に直列化され、「採番順＝コミット順」が構造的に保証される**（＝低いversionが後から現れる状況が同一ユーザー内で発生し得ない）
- versionは**ユーザーごと・全テーブル共通の単一タイムライン**。クライアントのカーソルは1ユーザーにつき1整数
- **1つの業務操作（1トランザクション）につき `next_sync_version()` は1回だけ呼び、そのトランザクションで書き換える全テーブル・全行に同じversionを設定する**（1版=1つの完結した変更グループ）
- `sync_versions` 行はアカウント作成時（`handle_new_user` トリガ）に必ず生成する。採番関数内の初回INSERT分岐は持たず、行が無ければ例外にする
- 差分取得はテーブル別ページングを行わず、`pull_sync_batch` による全テーブル一括方式とする（ADR-008）
- `updated_at` はLWW（フィールド競合解決）専用に残す。カーソルには使わない

## 帰結

- 同一ユーザーの書き込みはユーザー単位で直列化される（スループット上限が生まれるが、単一ユーザーのアプリ操作頻度では問題にならない）
- 版数逆転耐性・削除墓標・同時トランザクションのテストが#501・#511の受け入れ条件になる
