# 装備合成の実DB・Edge統合：応答喪失と古い結果の再送（2026-11-06）

計画④ / #699・#931 / T07。#930マージ後のmain `967d2ed6`が基準。

## 目的と対象

#930の装備復活防止を、実ローカルDB/Edge、JWT、共有gameCloud/Edge invoker、pull/cache、Web/Mobileの実ゲームストアまで接続して確認する。[統合テスト](../supabase/integration/synthesis-seed-race.test.ts)は次の4条件を両方で実行する計8件。

- 応答先行：通常応答で素材を消費し、同期/同一キー再送でも同じ結果1点に留まる。
- 同期先行：結果を実RPCで装備してから受信し、遅い応答や再送が装備状態を戻さない。
- 確定後に応答喪失：サーバー成功後の本文を消費してから通信例外を発生させる。実pullで結果を受信し、実sell_itemで売却して墓標とXPを受信後、元の合成キーを再送しても装備を復活させない。
- 次の合成後：最初の結果と別の素材2点を実synthesize_itemsへ送り、次の結果を受信する。最初の遅い応答・同一キー再送で消費済み装備を作り直さない。

素材3点の墓標と元の結果が同じversionで作られること、SQLの冪等台帳と実Edge応答の結果ID/templateが一致することを確認する。売却・次の合成後も、元のキーは同じ結果を返す契約であることを検証する。クライアントは古い結果を再生成せず、後の所持品/装備状態・XPを維持する。各応答の反映直後に、DBの現在の所持品との比較だけを行い、後続pullで誤りが修復されて合格しないようにする。

同じ合成キーを2回再送しても合成台帳は1操作分（次の合成ケースだけ2操作分）。売却XP・報酬台帳は1回分、素材・結果の墓標は維持される。最後に反復pullでも一致することを確認する。

## 実行と安全な範囲

既存の`supabase` CIが`npm run test:sync -- --integration`で自動実行する。環境変数5項目が無い通常テストでは8件をskipする。新ファイルを含めた型検査とLint、通常環境での読み込み/skipも確認する。実DBの8件はCIの実行ログでskipなしの成功を確認してからPR本文へ記録する。

全URLをassertLocalSyncEnvironmentで検証してからDB接続/一時アカウント作成を行い、クラウド接続先は拒否する。fixtureは作成したアカウントのXPと装備6点のみをユーザーロック/version付きで準備し、後片付けはそのアカウントだけを削除する。このテストからDB reset/truncate・既存ユーザー/承認済みstaging A/Bの操作は行わない。トークン/鍵は環境変数とメモリだけで扱い、保存・出力しない。

Nativeディスクと応答の喪失/ストア反映タイミングはテストで制御する。実Expo Router/端末UI/実回線やOS終了後の永続復旧の合格とは区別する。実stagingで必要な素材を揃えて行う合成の確認は引き続き残す。
