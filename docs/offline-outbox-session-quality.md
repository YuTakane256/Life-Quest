# オフライン再送の停止・認証帰属・再開（#735）

## 対象と変更

Web / Mobile共通のoutboxを対象とする。画面統一後の品質確認の一部であり、
DB・RPC引数・保存形式・報酬計算は変更しない。保存済みキューは初期化しない。

- 送信前の保存待ちから戻った時点でも、停止・認証スコープ失効を確認する。
- 保存は同じキュー内で直列化し、stopはenqueueの保存完了も待つ。
  保存失敗時も他の保存・停止の完了を待ち、共有停止バリアへ拒否を持ち越さず次のログインで回復可能にする。
- 認証通知開始時点で旧キューを公開対象から外す。前段の非同期フック待ち、
  ロード待ち、送信先取得待ち、結果待ちでも古いキューを再び有効にしない。
- 遅れたenqueueの結果を新アカウントのエンティティ依存追跡へ混入させない。
- Edgeは既存の所有者確認・スコープ確認を利用する。
- RPCはSDKのセッション所有者を確認し、そのJWTをAuthorizationヘッダーへ固定する。
  SDKが後で別アカウントのトークンを取得しても送信ヘッダーを置き換えない。
  トークンはpayload・永続キューへ保存しない。
- 所有者不一致・不明・未認証・HTTP401は操作を失敗扱いで破棄せず、認証回復待ちにする。
  接続回復や手動再送だけでは解除せず、同じユーザーのログイン通知後に同じopIdで再開する。
- ログアウト通知が次のログインに追い越されても、失効した同一ユーザーのキューは再利用せず、
  停止・保存完了後にそのユーザーのnamespaceから復元する。

## 親子の連続登録時の依存欠落（2026-10-28 / #856）

[Nativeの未送信親子タスクの記録](staging-native-pending-restart-20261028.md)では、
親子のpayload参照は正しい一方、両操作の`dependsOn`が空だった。
共有controllerが親の操作IDを記録するのは保存の`await`後だったため、
親の完了を待たずに子を追加する新規フォームの呼び出し順で依存先が見つからない。
修正前の自動テストでは依存欠落に加え、親がHTTP422で恒久失敗した後も、
子の作成・完了が送信されることを再現した。

操作IDは既存のUUID生成処理で先に決め、下位outboxへ同じIDを渡す。
エンティティ→操作IDの追跡を保存待ちより前に予約することで、
同じ呼び出しの並びでも親→子→完了の依存を保存する。
登録拒否時は予約を戻し、保存失敗で下位キューに操作が残る場合は追跡も残す。
保存待ち後に古い予約を再登録しないため、認証切替後の追跡へ混入させない。

`packages/core/src/cloudOutboxController.test.ts`に次の回帰を追加した。

- 親・子・子の完了を待たずに登録しても、依存先の操作IDをメモリと保存値に保持する。
- 親が恒久失敗した場合、子・子の完了は依存失敗となり送信されず、独立した操作は送信される。
- 親の最初の保存が失敗しても、メモリに残る親を後続の依存先として保持する。
- 親の保存待ち中にA→Bへ切り替えても、Aの依存先をBの操作へ持ち越さない。

Web/Mobileが使う共有controllerの修正で、画面・DB/RPC・保存形式・報酬計算の変更はない。
過去の空`dependsOn`を持つ保存済み操作の修復・再送は行わない。
再起動後に新規追加する操作の依存追跡の再構築は#856では対象外とし、次節の#858で対応した。
インメモリストレージと偽RPC/Edgeでの確認であり、新たなstaging実操作・端末試験は行っていない。
前回記録を「依存付きキューを確認済み」に読み替えず、T05の残項目も維持する。

## 再起動後の依存追跡と、後から追加された子の失敗（2026-10-29 / #858）

controllerを新しく作るとエンティティ→操作IDの追跡は空になり、保存済みの親に対して
再起動後に子を追加しても依存を張れなかった。修正前の自動テスト4件で、
復元した親子の依存欠落、親の送信中失敗後の子の誤送信、既存の失敗/競合への子の誤送信を再現した。

保存キューのロードと認証スコープの確認後、自動送信・ready状態の購読通知より前に追跡を復元する。
対象は既存の`upsert_task` / `upsert_subtask` / `delete_subtask` / `upsert_habit`の`p_id`と、
`set_habit_log`の`p_habit_id`。アプリの作成/更新・子の差分削除が追跡している操作で、
保存順で後の操作をそのエンティティの最新として扱う。未知の操作・空文字・文字列でないIDは追跡しない。
同じIDのA/B読込が重なっても、失効したAのロード結果をBの追跡へ混ぜない。

恒久失敗時の既存cascadeだけでは、その後に登録された子は失敗へ遷移できない。
そこで新規enqueue時に依存先が`failed` / `conflict`なら、子も`failed`・`dependency`として保存し、
既存の恒久失敗通知へ渡す。子孫も同じ扱いとなり送信しない。独立した操作の送信は継続する。

`packages/core/src/cloudOutboxRecovery.test.ts`は、次をモック/インメモリストレージで確認する。

- 別のcontrollerから同じ保存領域をロードし、親子の操作IDと元の依存配列を保持して、新しい完了操作の依存を保存する。
- 復元した親の送信中に子を追加した後、親が恒久失敗すると子を送信せず、独立操作だけ続ける。
- 保存済みの失敗/競合を再送せず、新しい子と子の完了を依存失敗にし、保存・通知する。
- 既知5種類の最新操作を復元し、未知/不正フィールドを追跡しない。
- 遅いAのロード後も、現在のBのキューだけから依存先を復元する。

画面・DB/RPC・保存形式・報酬計算は変えず、既存操作の`opId`・payload・`dependsOn`は書き換えない。
過去の空依存を持つ保存済み子の補修、既存failedの救済/再送・消去は行っていない。
stagingやSimulatorのデータは操作していない。実プロセス終了・実回線断・実サーバー再送の追加試験ではなく、
T05/計画④全体の合格にはしない。前回の[実操作記録](staging-native-pending-restart-20261028.md)は当時の条件のまま保持する。

## 境界と残る実環境確認

これはモック/インメモリストレージ/偽fetchでの回帰確認であり、stagingの実アカウントや実機試験の代替ではない。
すでに開始したHTTP・ストレージI/Oを取り消す保証はない。開始済みのAの要求はAのJWTのまま完了し得る。
その結果を旧画面へ反映せず、再送では同じopIdによるサーバー冪等性（ADR-004）を利用する。
退会とストレージ削除を単一トランザクションにする変更は含まない。

stagingの専用アカウントで、Web→Mobile / Mobile→Web、オフライン編集→再接続、
保留中のログアウト→別アカウント→元アカウント、再起動、期限切れ認証を確認する。
元のユーザーだけへ反映され、タスク完了・習慣ボーナス・売却の再送で報酬が重複しないことを確認する。
宝箱・合成・バトルは従来どおりrequest/response専用で、このoutboxの対象外。
