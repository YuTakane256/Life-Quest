# オフライン再送の停止・認証帰属・再開（#735）

## 対象と変更

Web / Mobile共通のoutboxを対象とする。画面統一後の品質確認の一部であり、
DB・RPC引数・保存形式・報酬計算は変更しない。保存済みキューは初期化しない。

- 送信前の保存待ちから戻った時点でも、停止・認証スコープ失効を確認する。
- 保存は同じキュー内で直列化し、stopはenqueueの保存完了も待つ。
  保存失敗時も他の保存・停止の完了を待ち、共有停止バリアへ拒否を持ち越さず次のログインで回復可能にする。
- 認証通知開始時点で旧キューを公開対象から外す。前段の非同期フック待ち、
  ロード待ち、送信先取得待ち、結果待ちでも古いキューを再び有効にしない。
- 遅れたenqueueの結果を新アカウントのエンティティ依存追跡へ混入させない。
- Edgeは既存の所有者確認・スコープ確認を利用する。
- RPCはSDKのセッション所有者を確認し、そのJWTをAuthorizationヘッダーへ固定する。
  SDKが後で別アカウントのトークンを取得しても送信ヘッダーを置き換えない。
  トークンはpayload・永続キューへ保存しない。
- 所有者不一致・不明・未認証・HTTP401は操作を失敗扱いで破棄せず、認証回復待ちにする。
  接続回復や手動再送だけでは解除せず、同じユーザーのログイン通知後に同じopIdで再開する。
- ログアウト通知が次のログインに追い越されても、失効した同一ユーザーのキューは再利用せず、
  停止・保存完了後にそのユーザーのnamespaceから復元する。

## 自動回帰の証拠

- `packages/core/src/syncOutbox.test.ts`：保存待ち中のstop/スコープ失効、送信開始済み操作の停止、
  同じ操作IDでの再開、FIFO・依存・認証回復待ち。
- `packages/core/src/cloudOutboxSession.test.ts`：認証フック到達前の失効、遅れたロード・enqueue、
  A→logout→A、Edgeの所有者確認、RPCの所有者とHTTP401分類。
- `src/platform/cloudOutboxTransport.test.ts`：Webアダプタの所有者確認・再ログイン後の再送。
  実際のSupabase SDKと偽fetchを組み合わせ、SDKが別JWTを取得しても明示Authorizationが保持されること。
- `apps/mobile/src/platform/cloudOutbox.test.ts`：Mobileアダプタも所有者確認・同じp_keyでの再送を使うこと。

## 境界と残る実環境確認

これはモック/インメモリストレージ/偽fetchでの回帰確認であり、stagingの実アカウントや実機試験の代替ではない。
すでに開始したHTTP・ストレージI/Oを取り消す保証はない。開始済みのAの要求はAのJWTのまま完了し得る。
その結果を旧画面へ反映せず、再送では同じopIdによるサーバー冪等性（ADR-004）を利用する。
退会とストレージ削除を単一トランザクションにする変更は含まない。

stagingの専用アカウントで、Web→Mobile / Mobile→Web、オフライン編集→再接続、
保留中のログアウト→別アカウント→元アカウント、再起動、期限切れ認証を確認する。
元のユーザーだけへ反映され、タスク完了・習慣ボーナス・売却の再送で報酬が重複しないことを確認する。
宝箱・合成・バトルは従来どおりrequest/response専用で、このoutboxの対象外。
