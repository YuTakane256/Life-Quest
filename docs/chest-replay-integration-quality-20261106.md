# 宝箱開封の実DB・EdgeとWeb/Mobile反映の統合検証（2026-11-06）

## 確認する境界

開封hookやHTTPハンドラーだけの回帰では、確定応答・通常pull・売却の到着順が重なった際の、所持品・獲得履歴・演出イベント・戦闘解放の整合性を一緒に確認できない。

[統合テスト](../supabase/integration/chest-seed-race.test.ts)を既存のSupabase CIに追加する。実JWTと共有game clientでローカルEdge Functionへ送信し、SQLで確定した後の成功HTTP応答だけを保留する。通常の本人RLSで`pull_sync_batch`を読み、実cache/canonical反映・Web/Mobileストア・開封判断runnerを使用する。NativeのディスクとHTTP応答の遅延/喪失をスタブにし、DB・抽選・冪等処理を代替しない。

## 10ケース（各5件×Web/Mobile）

| ケース | 主な照合 |
| --- | --- |
| 木の応答先行 | 次のpullより前にサーバーIDの装備・開封済み・演出イベントを一度反映 |
| 木の同期先行 | 保留中に装備を装着してpullし、遅い開封応答が装備状態を巻き戻さず、演出も追加しない |
| 木の成功応答喪失→同期→売却 | 同キーの実HTTP再送で元の結果を取得しても、売却済み装備を再生成せず、獲得履歴は保持 |
| 青の応答先行 | 装備なしの確定結果・開封・戦闘解放・スターター演出イベントを反映し、XP/消化数を増やさない |
| 青の成功応答喪失→同期→再送 | 通常pullで解放済みとなった後の同キー再送で、装備・演出・XPを重ねない |

各ケースで実SQLの確定receipt・宝箱/装備version・本人の所持品と開封済み状態・戦闘解放・XPを照合する。各応答直後の比較では再seedしないため、後続pullによる修復で一時的な重複を隠さない。同キー再送を2回、別キーでの開封済み409拒否、反復pull後も照合する。無関係な装備と未開封の別宝箱を保持し、ローカル抽選fallbackは呼ばれないことを確認する。

売却では実`sell_item`を通し、売却台帳1件・レアリティ別XP・装備の削除墓標を照合する。獲得履歴の装備参照には墓標を使い、所持品には復活させない。演出はストアのイベント同一性を確認し、描画されたアニメーションの実機確認とは区別する。

## 実行と安全な範囲

`npm run test:sync -- --integration`で既存の実DBテストと一緒に実行する。接続情報がない通常のローカル全体テストでは10件をskipし、成功した実DB検証とは数えない。最終HEADのSupabase CIで新しい10件がskipなく実行されたことをログで確認し、全体/型/Lint/secrets/ビルド・通常CI3件・独立レビューの確定結果はPR/Issueへ記録する。

接続・アカウント作成より前に既存のloopback限定ガードを実行する。各ケースでこのテスト専用の一時アカウント・fixtureだけを作成し、保留応答を解放して処理終了後に本人を削除する。DB reset/truncateや既存ユーザーの後始末は追加しない。

本番コード・DB/RLS/API・抽選/報酬・保存形式・画面・依存は変更しない。実stagingと承認済みA/B・利用データ・OS/Simulator/Dockerを操作しない。UI変更がないため比較画像は追加しない。実staging・端末UI・プロセス/OS終了後の永続復旧やネットワーク全障害の合格とは扱わない。④継続、⑤未開始。マージ・配布・デプロイは行わない。
