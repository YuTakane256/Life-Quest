# 初回移行・端末バックアップの認証スコープ分離

対象: #731。[表示ストアの境界](account-boundary-quality.md)に続き、初回移行の
非同期処理を確認します。Web基準の初回移行とMobileのバックアップ後置換という
[ADR-011](adr/011-web-first-migration.md)の方針、DB、Edge Functionの本文、報酬量は変更しません。

## 修正したこと

- WebでAの`profiles.imported_at`取得を待つ間にログアウト/別ユーザーへ切り替わると、
  待機後に現在のストアを読み、旧A向けに始めた移行を新セッションで送信していました。
  認証スコープ変更後はスナップショット作成・送信・成功扱いを中止します。
- 同じAでもA→B→AやA→ログアウト→Aは別スコープです。旧処理を再利用しません。
  旧Aの遅い失敗がBや新Aの移行状態を初期化しないよう、処理の識別も行います。
- 同一スコープの重複ログイン通知は同じ移行Promiseを待ちます。旧実装のように即時returnして
  後続の同期フックが移行を追い越すことを防ぎます。プロフィール取得失敗も次回通知で再試行可能です。
- Webの初回移行呼び出しでは、共有Invokerへ任意の`isActive`オプションを渡します。
  トークン取得後・401 refresh後の送信前にも確認するため、古い本文を新セッションの
  トークンで送信/再送する待機窓を防ぎます。オプションはHTTP本文に含めません。
  オプションなしの既存呼び出しは従来の認証・401再試行のままです。
- Mobileは既存バックアップ確認と各ストアのhydration待機後にスコープを確認し、
  新セッションのデータを旧ユーザーのバックアップキーへ保存しません。
  同一ユーザー・同一スコープの処理は待機を共有し、重複保存で初回コピーを上書きしません。

初回ログインの匿名データは従来どおり移行元です。Mobileの既存バックアップは保持し、
同じユーザーの単なる再通知では処理を無効にしません。ユーザー別キャッシュの削除や、
未承認Mobileコンテンツの自動統合も行いません。

## 自動回帰

```bash
npx vitest run src/platform/cloudMigrationSession.test.ts apps/mobile/src/platform/cloudMigrationSession.test.ts src/platform/cloudMigration.test.ts apps/mobile/src/platform/cloudMigration.test.ts packages/core/src/edgeFunctions.test.ts
```

実ストア・制御可能なPromise・モック保存領域と、実際の共有Invokerを組み合わせ、
以下を検証します（実Supabaseへの接続や実機操作ではありません）。

- profiles取得中のログアウト/A→B/A→B→A、トークン取得・401 refresh中の切替
- 重複通知が移行/バックアップの完了まで後続フックを待機させること
- 旧Aの遅い失敗、プロフィール取得失敗からの再試行
- Mobileの既存コピー保持、読み込み/hydration待機中の切替、読み込み失敗からの再試行
- 失効した同名ユーザーの処理が新処理の待機管理を破壊しないこと
- Invokerの既存認証・401再試行・user_id除去、および有効なガードでの通常送信

## 保証しないこと・次に残る確認

- 認証ライフサイクル通知のスコープガードであり、JWTの本人確認や認可の代替ではありません。
  SDKが切替を通知する前の状態変化や複数タブ協調までは保証しません。
- 既に開始したHTTPリクエストやAsyncStorage書き込みを取り消し/巻き戻しません。
  開始済み保存が切替後に完了する場合でも、保存内容は開始前に直列化したスナップショットです。
  退会時の削除と開始済み保存との原子性を保証するものではありません。
- Mobile設定画面の`getPendingMobileContent`/承認操作は別の手動フローです。
  #731では対象外です。候補表示・承認の帰属・再試行・画面更新は
  [後続の#733](mobile-manual-import-quality.md)でまとめて対応します。
- 実Supabaseの2アカウントE2E、Web↔Mobile、オフライン復帰、iOS/Android実機は
  [全体の品質確認](mobile-web-implementation-roadmap.md)で別途検証します。

この変更は画面の追加ではなくデータ安全性の修正です。実行結果・CI・独立レビューはPR本文へ記録します。
