# 受信同期の認証待ちと復帰（2026-10-31）

## 問題

送信キューが空でも、受信RPCだけがHTTP401になる場合がある。従来は一般の受信失敗として「接続を確認して再試行」と案内し、自動トリガでも繰り返し受信していた。同じアカウントの再認証通知も、動作中のハンドルがあるため無視されていた。

## 変更

- [共通fetcher](../packages/core/src/cloudPull.ts)に固定文言の`CloudPullAuthError`を追加し、両版のRPC実HTTPステータス401と、SDKセッション消失/所有者不一致を認証待ちとして伝える。
- SDKセッション読込の例外・エラーは一時失敗として扱う。503等やエラー本文の「401」という文字列から認証待ちを推測しない。受信中に同じ所有者のトークンが更新済みなら、古いトークンの遅い401は再試行できる失敗として扱い、認証待ちに固定しない。
- [共通同期状態](../packages/core/src/cloudSyncState.ts)に受信の`auth-required`を追加。pushが空でも注意表示と既存の再ログイン案内を使い、「今すぐ同期」を無効化する。最後の成功時刻を保持する。
- [Web](../src/platform/cloudSync.ts)と[Mobile](../apps/mobile/src/platform/cloudSync.ts)は、認証待ち中の手動同期・Realtime・再接続・定期受信を止める。接続状態の変化だけでは認証待ちを解除しない。
- 同じアカウントのログイン/トークン更新通知で、認証待ちのハンドルだけ作り直す。両版の実SDK `TOKEN_REFRESHED` リスナーから、[共有ライフサイクル](../packages/core/src/authLifecycle.ts)の専用通知を通す。この通知は現在の所有者に限定し、認証scope・初期化完了待ちを変更せず、ログイン用の移行/ストア初期化フックは実行しない。パスワード復旧ゲート中の通知では再開しない。outbox先行・キャッシュ復元・0からの受信再構築という既存の起動処理を使う。通常の同一ユーザー通知は既存のハンドルを維持する。
- 古いハンドルの遅い401は、別アカウントの状態・保存先へ反映しない。

状態はメモリ上だけで、DB/RLS/API/保存形式/報酬/依存版を変更しない。キャッシュ・キュー・カーソルの消去や、別アカウントへのデータ移動は行わない。

## 検証範囲

[両版のセッション境界テスト](../src/platform/cloudSyncSession.test.ts)と[Web設定の操作テスト](../src/components/ui/CloudSyncSettings.test.tsx)で、新規5件を修正前に全失敗として再現。認証待ち表示、手動/自動同期の停止、データ/成功時刻保持、同一所有者での再開を確認する。
追加で自動同期401、遅い旧アカウント401、SDK一時障害、本文に401を含む503、共有状態とエラー分類を確認する。独立レビューで実SDK更新イベントの配線不足を指摘されたため、実リスナー→専用通知→停止中の両版pullの復帰を通す回帰を追加した。通常通知ではハンドルを維持し、別所有者の通知とパスワード復旧中は再開しない。受信中の更新による古い401と、通知遅延中のアカウント切替も検証する。

[実DB統合](../supabase/integration/two-client-sync.test.ts)には、SDKの既定tokenが有効でも、明示した無効JWTのHTTP401が認証信号として残るケースを追加する。ローカル環境変数がない通常の単体テストではskipとなり、Supabase CIで実行する。

UIは既存の同期カード・共通メッセージ・ボタン制御を利用する。配置・素材・テーマの変更はなく、新規比較画像は追加しない。認証待ちが一時失敗と混同されないことを操作テストで確認する。

## 残る確認

再認証は既存のログイン操作/認証通知を使用する。新しいプロバイダー設定、自動ログアウト、強制的なtoken更新、認証ボタンや画面の追加はしない。
実ユーザー/stagingや秘密値の操作、配布/デプロイも行わない。署名済み実機の認証/OS検証、実環境設定・監視、依存等の残課題は[#871](https://github.com/YuTakane256/Life-Quest/issues/871)で継続する。計画④全体の完了や⑤への移行、安全性全体の保証を意味しない。
