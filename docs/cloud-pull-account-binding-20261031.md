# 受信同期のアカウント固定（2026-10-31）

2026-10-31追記: [受信同期の認証待ちと復帰](cloud-pull-auth-recovery-20261031.md)で、受信だけのHTTP401にも既存の再ログイン案内を適用し、同じ所有者の再認証後に同期を再開する。以下は各対応時点の記録。

## 対応した問題

Web/Mobileの受信同期は、保存先をログイン時のuser IDで決める一方、`pull_sync_batch`の認証にはSDKの送信時点のセッションを使っていた。
SDKだけ先にA→Bへ切り替わり、アプリの切替通知が遅れると、Bの正当な応答をAのキャッシュ・画面へ適用できた。
これはクライアントの保存先との対応の問題であり、RLSの迂回を確認したものではない。実運用での発生履歴を調査した記録でもない。

## 変更

- [共有fetcher](../packages/core/src/cloudPull.ts)で、RPC前にSDKのセッション所有者と同期ハンドルの所有者を照合する。
- 取得したトークンを、そのリクエストの`Authorization`へ明示する。送信時にSDKの既定トークンが変わっても置き換えない。
- 応答後も所有者を確認し、セッション消失・別アカウントへの切替・停止済みハンドルではバッチを返さない。同じ所有者のトークン更新は許容する。
- 拒否時はバッチ適用・キャッシュ更新・カーソル前進を行わない。同じアカウントへ戻れば通常の次回同期で再試行できる。
- セッション取得・RPC失敗は固定のエラー文言へ置き換え、生の診断やトークンを転記しない。
- runnerは失効済み処理の遅い失敗を破棄する。現行処理の失敗は従来どおり呼出元へ通知する。

[Web](../src/platform/cloudSync.ts)と[Mobile](../apps/mobile/src/platform/cloudSync.ts)に同じfetcherを接続する。
outbox先行の再接続処理、Realtime・定期受信、データ保存形式、報酬、サーバーJWT検証・RLS・API・DBは変更しない。

## 検証

- [両版セッション境界テスト](../src/platform/cloudSyncSession.test.ts): SDKだけの切替、受信途中の切替、セッション消失を追加。新規6件が修正前に全失敗することを確認した。
- [共有fetcherテスト](../packages/core/src/cloudPullSession.test.ts): 不一致/空の認証、非公開診断、停止、応答後の所有者確認、同じ所有者の更新、再試行を検証。
- 実際のSupabase SDKとmock HTTPを通し、既定Bトークンより明示Aトークンが優先されることを確認。
- [実DB統合テスト](../supabase/integration/two-client-sync.test.ts): 既存の2テストユーザーを利用。捕捉済みのAセッション情報とSDKの既定Bトークンを意図的に分け、RLS下でAの行だけ返ること、応答後の所有者変更で拒否することを検証する。
- [再接続順序](../src/platform/cloudSyncRecoveryOrdering.test.ts)や従来の世代切替・保存中断の検証を維持。

実DBテストはローカルSupabaseを必要とし、環境変数がない通常の単体テストではskipになる。PRのSupabase CI結果と単体テスト成功を区別する。
画面配置の変更はないため比較画像は追加しない。

## 残る確認

この照合はSDKセッション情報を前提とする。改変されたクライアント、盗難トークン、端末侵害に対する認可はサーバーJWT検証/RLSの役割であり、クライアントのuser ID照合は代替にならない。
HTTP401を認証回復待ちとして表示する専用UIや再認証導線は今回変更しない。受信失敗は既存の失敗表示となる。
既存キャッシュの暗号化/消去、ログの消去、実プロジェクト設定変更、実ユーザーやstagingの操作、配布/デプロイは行わない。

計画④の認証・同期境界の修正であり、④全体完了や⑤への移行、安全性全体の保証は意味しない。実環境/依存の残課題は[#871](https://github.com/YuTakane256/Life-Quest/issues/871)で継続する。
