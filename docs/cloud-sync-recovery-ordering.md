# 自動同期の未送信処理順序とキャッシュ復元（#868）

計画④ [#699](https://github.com/YuTakane256/Life-Quest/issues/699) / T04・T05の準備中に見つかった同期不具合を修正する。
今回はWeb/Mobileの実同期アダプターの自動回帰であり、実staging・OS回線断の確認記録ではない。

## 問題と変更

- Web/Mobileの起動・再接続・前景復帰は未送信キューを処理してから受信していたが、
  Realtimeと5分周期はその処理を迂回していた。再試行待ちの変更があると、古いサーバー状態で楽観表示を上書きし得る。
  全ての自動トリガを同じ未送信処理→受信の経路へ揃えた。
- Mobileでは、非同期の保存キャッシュ読込を待たずにRealtime・手動受信が進み、後から古いキャッシュで上書きされる経路があった。
  全受信経路が同じ初期読込の完了を待つようにした。読込失敗時も次の受信で再構築を試みる。
- Mobileの保存カーソルだけが進んでいると、欠けたキャッシュの行を差分受信で補えない。
  既存Webと同様、ハンドルごとの初回はversion 0から取得し、そのハンドルが実際に反映した位置から差分取得する。
  保存キーは維持する。初回の読込量は増えるため、大量データでの起動性能は今後確認する。

DB/API・RLS・報酬計算・保存形式・画面の変更はない。キャッシュやキューは初期化しない。
既に実行中のpullと、その後に追加される操作の全ての競合を解消したという意味ではない。

## 回帰テスト

[Web/Mobile共通の18ケース](../src/platform/cloudSyncRecoveryOrdering.test.ts)では、実際のcloudSync・共有pull runner・
キャッシュ変換/保存を使う。通知、SDK通信、outboxの完了結果、初回キャッシュ読込、保存領域はスタブ。
実outboxの送信保証は既存の[同期境界回帰](sync-recovery-integration-quality.md)と併せて確認する。

| 条件（Web/Mobile各9ケース） | 確認内容 |
| --- | --- |
| Realtime・定期・前景復帰・再接続の各トリガ | 再試行待ちなら受信せず楽観表示を維持。キュー処理成功後の次の通知で受信・表示を更新 |
| 初回読込と未送信処理が両方待機 | 両方の完了前に受信しない |
| 初回読込中の明示flush | 読込完了を待ち、新しい受信行が後から消えない |
| 初回読込中にstop | 遅い読込と通知から旧ハンドルの受信を開始しない |
| 保存カーソルだけが先行 | 初回は0、受信済みの次回は反映位置から取得 |
| 初回キャッシュ読込失敗 | 保存カーソルを信用せず全件受信を試行 |

最初の12ケースを修正前に実行し、8件が失敗した。修正後に表示と復帰経路を追加し、18件が成功。
`npm run test:sync:unit`にも含め、既存の送信・認証境界と併せて190件が成功した。
