# パスワード再設定へ切り替わる際の同期分離（#866）

計画④ [#699](https://github.com/YuTakane256/Life-Quest/issues/699) / T06・T08の認証境界の修正。
[Nativeの期限切れ対応](staging-native-auth-recovery-20261029.md)で残確認としていた、
稼働中のAから別アカウントBの再設定セッションへ移る経路をWeb・Mobileで修正した。

## 問題と変更

以前は、`PASSWORD_RECOVERY`や復旧フラグ中の`SIGNED_IN`を通常ログインとして処理しないだけで、
既に動いているAの同期処理は失効させていなかった。
SDKがBのセッションへ変わると、Aの表示・キャッシュを扱う処理がBの認証で継続する余地があった。

- 再設定へ入る時点で報酬処理を待機させ、Aのライフサイクルを同期的に失効させる。
  既存のログアウト用フックで同期・outbox・表示の片付けを行い、完了まで再設定フォームを有効にしない。
- 重複するSDK通知は同じ片付けの完了を待つ。既に所有者のいない起動では、未知のキャッシュを無条件に初期化しない。
- Mobileの検証済み再設定URLも、PKCEコードを交換する前に以前の同期を止める。
  古い交換応答が、新しいログイン・キャンセル後にフォームを復活させないようにする。
- パスワード更新の前後でセッション所有者と処理の世代を確認する。
  更新中にログアウトや新しい再設定セッションへ変わったら、遅い応答で通常同期を開始しない。
- キャンセルも片付けを待ち、途中で変わった新しい認証を上書きしない。
- 復旧フラグの読取・保存失敗でも以前の同期を停止する。無効なリンクの状態は通常ログイン通知だけで有効に戻さない。

通常ログアウトと同じ片付けにより表示は外れるが、サーバーのデータと所有者別の未送信キューは消さない。
DB/API・RLS・報酬計算・保存形式・画面レイアウトの変更はない。

## 検証した範囲

[回帰テスト](../src/platform/recoverySessionIsolation.test.ts)は、実際の認証サービス・共有ライフサイクル・
outboxコントローラーと、スタブの認証SDK・メモリ上の保存領域を組み合わせる。
**Supabase実アカウントへのメール送信・パスワード変更・SDKの実PKCE通信の検証ではない。**

最初の10ケースは修正前に失敗した。保存失敗と新しい再設定への切替を加え、Web/Mobile各7ケース、計14ケースを確認した。

| 条件 | 確認結果 |
| --- | --- |
| Aの稼働中にBの`PASSWORD_RECOVERY`、または復旧フラグ中の`SIGNED_IN` | Aのguardが直ちに失効し、停止完了までフォームは待機。Bのパスワード更新後だけBのライフサイクルを開始 |
| Aの親子2操作が未送信 | 実outboxで親の操作ID・子の依存を生成して保存。停止とBへの切替後もAの操作ID/payload/依存は同じで、Bのキューへ持ち込まない |
| 再設定通知が重複 | 先行するAの片付けを追い越してフォームを有効にしない |
| 復旧フラグの保存失敗 | Aの同期を止め、パスワード更新を呼ばず、無効状態を表示 |
| 片付け待機中にログアウト | 遅れた完了でフォームを有効にしない |
| 更新要求中にログアウト、または別Cの再設定へ切替 | 遅い成功応答で新セッションを通常ログインにしたり、再設定状態を解除したりしない |

既存のWeb/Mobile認証テストも、フォーム有効化が片付け完了後になる契約に合わせて確認する。
stagingのデータ・テストアカウント・保存済み認証には触れていない。

## 残確認

実際のメールリンク・PKCE通信・プロバイダー・実機での再設定フロー、期限切れと未送信/処理中操作を組み合わせた起動は別途残す。
今回のSDK通知スタブによる確認を、実アカウントの再設定完了や計画④全体の完了とは扱わない。
