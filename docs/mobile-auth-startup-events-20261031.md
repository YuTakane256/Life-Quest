# Mobile起動時の認証イベント保持（2026-10-31）

## 問題

Mobileは保存済みのパスワード復旧ゲートをAsyncStorageから復元してから認証を有効にする。その待機中、SDKの通知を1つの共有変数へ無条件で上書きしていた。
初期ログイン/ログアウトの後にTOKEN_REFRESHEDやUSER_UPDATEDが届くと、初期化に必要な通知が失われ、報酬・同期の認証確認が完了しない場合があった。復旧通知が後続の通常ログイン通知へ置き換わる問題と、旧リスナーの遅い読込/通知が新しい初期化へ影響する経路も修正する。

## 変更

[Mobile auth](../apps/mobile/src/platform/auth.ts)で、起動時の通知をリスナー単位で扱う。

- 初期セッション・ログイン・ログアウト・パスワード復旧を保持し、通常の更新通知で上書きしない。最新の本人変更だけを初期化する。
- 保持するのは最大1つの通知とユーザーIDだけ。TOKEN_REFRESHEDは初期化通知がない場合の代替として保持し、不要な通知を配列へ蓄積しない。
- 復旧意図は後続SIGNED_INやリスナー置換をまたいで維持する。保存が完了するまで通常ログインへ進めず、既存の更新/キャンセル処理によるゲート保存で意図を解決する。
- リスナーの世代を比較し、停止/置換後のSDK通知、遅い読込結果・失敗、旧リスナーの解除が現在の初期化を変更しないようにする。
- ゲート読込中に復旧/キャンセルの保存が進んだら、最新の保存完了後に読み直す。古い読取結果でキャンセルしたゲートを復活させない。
- 読込・保存に失敗した場合は通常ログインへ進めず、既存の無効/復旧待ち表示を維持する。

認証SDK callbackは非同期処理をawaitせず戻る。実アプリでは同期/outbox等の登録後に認証リスナー、続いて認証リンクリスナーを開始する既存の順番を維持する。
[既存の所有者チェック](../apps/mobile/src/platform/cloudSessionRecovery.ts)、[共有認証ライフサイクル](../packages/core/src/authLifecycle.ts)、outbox、パスワード更新/キャンセルの認証・保存経路を利用する。
Webの通知処理、DB/RLS/サーバーAPI/報酬ルール/保存形式/プロバイダー設定/依存版は変更しない。ゲートは既存キーの同じ値を使用し、タスク等やキューを削除・移動しない。

## 検証

[Mobile auth回帰](../apps/mobile/src/platform/auth.test.ts)で最初の5件が修正前に全失敗することを確認した。遅いゲート読込の間にSDK通知を発火させ、解放後の最終状態を検証する。

- 初期ログイン/匿名起動/ログアウトと更新通知、旧リスナー通知/読込、旧解除と新しい本人確認。
- 復旧通知の後続ログイン、ゲート保存失敗、保存中ログアウト、リスナー置換、キャンセル後の古い読込。
- [実ライフサイクル/outboxを使う回帰](../src/platform/recoverySessionIsolation.test.ts)で、Aへの復帰は同じ操作ID/内容を保持し、最新Bだけの初期化でもAの操作をBへ移さないことを確認。SDK・保存はスタブであり、実アカウント操作の確認ではない。

既存のWeb/Mobileの受信同期・復旧ゲート回帰も実行する。テスト間の復旧意図は通常のキャンセル契約で片付け、初期化関数でセキュリティ状態を直接消すAPIは追加しない。
画面配置・素材の変更がないため、新しい比較画像は追加しない。

## 残る確認

実端末/実ストレージの全障害、任意のSDK通知順序、突然のプロセス終了やストレージ保存不能後の再起動を網羅した扱いにはしない。認証の正当性はSDK/サーバーの既存経路に委ねる。
実ユーザー/staging・秘密値・利用中の保存データを操作せず、配布・デプロイ・自動マージは行わない。計画④と[#871](https://github.com/YuTakane256/Life-Quest/issues/871)の実環境/依存等の確認は継続し、⑤へは進まない。
