# 戦闘結果の受信順序：実DB・EdgeとWeb/Mobileストア（2026-11-06）

計画④ / #699・#925 / T07。#924マージ後のmain `a075606d`が基準。

## 目的と対象

#922・#924で修正した、同期のXP反映後に遅い勝利応答で報酬を重ねる問題を、実際のSQL・Edge・pullデータと組み合わせて検証する。[統合テスト](../supabase/integration/battle-seed-race.test.ts)は、Web/Mobileそれぞれについて次の3通り、計6件を追加する。

- 同期をストアへ先に反映し、その後に勝利応答を適用する。
- 勝利応答を先に適用し、その後に同期を反映する。
- サーバーで結果を確定後、成功応答の本文を受信してから通信例外を発生させ、同期で復帰する。

認証は一時アカウントの実JWT、開始・決着は共有のgameCloud/Edge invoker、戦闘は実Web/Mobileストアと返された固定スナップショットを使用する。pull_sync_batchのページを実cacheへ取り込み、実canonical/seed経由で反映する。character/attemptの所有者・確定状態・版は架空データに置き換えず、そのままの受信データを使う。DBでも勝利時のcharacter/attemptが同じ正のversionになり、XPが報酬1回分だけ増えることを確認する。

同一キーの再送は、元のgranted=trueが返ることを明示的に確認する。別キーではgranted=false/already_resolvedとなり、いずれをストアへ渡しても二重加算しない。反復pull後も報酬台帳は1件、サーバー/端末XPは一致する。Webの履歴は1件、ステージ1の結果表示・履歴は、サーバーの選択ステージ4に差し替わらない。Mobileの結果表示もステージ1を維持する。

## 実行と安全な範囲

既存CIの`supabase`ジョブが`npm run test:sync -- --integration`で自動実行する。必要な環境変数が無ければ通常のunit実行では6件をskipする。全URLを既存のassertLocalSyncEnvironmentで検証してからDB接続・ユーザー作成を行い、クラウド接続先を拒否する。作成した一時アカウントだけをテスト後に削除し、DB reset/truncateは実行しない。鍵・トークンは環境変数/メモリのみで扱う。

今回のローカルDockerは停止中のため、手元では実DB成功を主張せず、CIで6件が実際に実行されたログを確認する。通常テスト・型検査・Lint・secrets・ビルドと、PR作成後の独立レビュー/最終HEADの通常CI3件の結果はPRへ記録する。
