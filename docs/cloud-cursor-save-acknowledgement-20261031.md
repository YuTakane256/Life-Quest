# 同期カーソル保存の成功確認（2026-10-31）

## 問題

Web/Mobileとも、カーソル保存の完了前にメモリ上の受信位置を進めていた。保存が拒否されても次回はその位置から受信するため、保存の再試行をしないまま「同期済み」へ戻れる経路を修正する。
これはカーソル保存の確認順の問題で、実ユーザーのデータ消失履歴を調査した記録ではない。

## 変更

[Web](../src/platform/cloudSync.ts)と[Mobile](../apps/mobile/src/platform/cloudSync.ts)で、保存APIの成功応答後にだけメモリ上のカーソルを更新する。完了時点でも同じハンドル/認証世代が有効か確認する。

- カーソル保存失敗時は、最後に保存成功を確認できた位置を再試行に使う。先行ページの確定分を保持し、後続ページは取得しない。
- 書込み後に失敗が返る場合も、結果を推測して位置を進めず同じ範囲を受信する。同じ行ID/versionでキャッシュへ再適用し、成功時に保存を確認する。
- 保存待ち中に別アカウントへ移った場合、既に始まった旧namespaceへの保存が完了しても、旧ページの続きを取得したり新アカウントの表示/状態を変更したりしない。
- 既に保存・表示できたキャッシュを巻き戻さず、失敗表示と最後の成功時刻を維持する。保存機能が回復すれば通常の同期操作で再開する。

保存キー・値の形式、起動時に0から再構築する契約、受信制御情報の検査、所有者/トークン固定、outbox先行処理は維持する。
DB/RLS/サーバーAPI/報酬計算/プロバイダー設定/依存版・キャッシュ変換は変更しない。

## 検証

[両版セッション回帰](../src/platform/cloudSyncSession.test.ts)に8件追加。最初4件は修正前に全失敗することを確認した。

- 保存前拒否/書込み後拒否の両条件で、保存済みキャッシュ・表示・最後の成功時刻を保持し、再試行のp_after_versionが最後の確認済み位置であることを照合する。
- 複数ページの途中でカーソル保存を失敗させ、先行ページ保持、後続送信停止、同じページの再適用、最終位置の保存を確認する。
- Aの保存を待たせてBへ切り替え、旧保存完了後もBの表示/同期状態とnamespaceが変わらないことを確認する。

実際の両版ハンドル/共有runnerを使い、SDKと保存APIはスタブで障害を注入する。[既存の再接続順序](../src/platform/cloudSyncRecoveryOrdering.test.ts)と共有受信回帰も実行する。実端末のディスク障害を再現した確認ではない。
画面配置・素材の変更はないため、新しい比較画像は追加しない。

## 限界と残課題

成功応答を確認する順序の修正であり、キャッシュ複数キーとカーソルを単一トランザクションにしたものではない。電源断・任意のクラッシュ・実ストレージ全障害の保証や、既に開始した書込みの取消は含まない。
実ユーザー/staging・秘密値・利用中データを操作せず、配布・デプロイ・自動マージは行わない。計画④と[#871](https://github.com/YuTakane256/Life-Quest/issues/871)の実環境/依存等の確認は継続し、⑤への移行や全体の安全性保証とはしない。
